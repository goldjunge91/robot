# Robot Package Cheatsheet

This document serves as a comprehensive README, cheatsheet, and setup guide for this ROS 2 robot package.

**Important**: This package is named `robot`. If you rename it, you must find and replace all instances of `robot` within the project files.

-----

## 📂 Project Structure

The workspace is organized with the source code located in `src/robot`. The `build`, `install`, and `log` directories are automatically generated by `colcon` and should not be version-controlled.

```txt
dev_ws_robot/
src/
└── robot/
    ├── CMakeLists.txt              # Build configuration
    ├── LICENSE.md                  # License information
    ├── package.xml                 # Package description and dependencies
    ├── README.md                   # This documentation
    ├── config/                     # Configuration files (RViz, controllers, etc.)
    │   ├── drive_robot_gazebo_rviz.rviz
    │   └── view_robot.rviz
    ├── description/                # Robot description (URDF/Xacro files)
    │   ├── gazebo_control.xacro
    │   ├── robot_core.xacro
    │   └── robot.urdf.xacro
    ├── launch/                     # Launch files to start nodes
    │   ├── launch_sim.launch.py
    │   └── rsp.launch.py
    └── worlds/                     # Gazebo world files
        ├── empty.world
        └── obstacles.world
```

## 🚀 Quickstart: Installation & Setup

Follow these steps to set up a new system (Desktop, Server, or Raspberry Pi).

### First 1: set your ROS-Distrib !! Important !!

To avoid repetition, define your ROS distribution as an environment variable. Run this command once per terminal session:

```bash
# Replace 'humble' with your ROS distro (e.g., iron, jazzy)
export ROS_DISTRO=humble
```

*Optional* To make this setting **permanent** for all new terminals, add it to your `.bashrc` file:

```bash
echo "export ROS_DISTRO=humble" >> ~/.bashrc
source ~/.bashrc
```

### Step 2: install system dependencies

With `ROS_DISTRO` set, you can install all required packages with the following commands.

```bash
# Update package lists first
sudo add-apt-repository universe -y
sudo apt install -y \
  software-properties-common \
  python3-colcon-common-extensions \
  joystick jstest-gtk evtest

# Add the ROS 2 GPG key and repository
sudo apt update
sudo apt install curl -y
sudo curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key -o /usr/share/keyrings/ros-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] http://packages.ros.org/ros2/ubuntu $(. /etc/os-release && echo $UBUNTU_CODENAME) main" | sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null

sudo apt update
sudo apt upgrade

# ROS Desktop (Recommended) Installation ROS RViz and other demos tutorials 
sudo apt install -y \
  ros-${ROS_DISTRO}-desktop \
  ros-dev-tools

# Install core simulation and control packages
sudo apt install -y \
  ros-${ROS_DISTRO}-gazebo-ros-pkgs \
  ros-${ROS_DISTRO}-ros2-control \
  ros-${ROS_DISTRO}-ros2-controllers \
  ros-${ROS_DISTRO}-gazebo-ros2-control \
  ros-${ROS_DISTRO}-xacro \
  ros-${ROS_DISTRO}-joint-state-publisher-gui \
  ros-${ROS_DISTRO}-urdf \
  ros-${ROS_DISTRO}-urdf-launch \
  ros-${ROS_DISTRO}-urdf-tutorial \
  ros-${ROS_DISTRO}-twist-mux \
  ros-${ROS_DISTRO}-ros2-controllers \ 
  ros-${ROS_DISTRO}-rqt-image-view \
  ros-${ROS_DISTRO}-moveit \
  ros-${ROS_DISTRO}-moveit-msgs \
  ros-${ROS_DISTRO}-moveit-ros-planning \ 
  ros-${ROS_DISTRO}-moveit-ros-planning-interface \
  ros-${ROS_DISTRO}-moveit-servo \
  

# Install useful tools and extensions
sudo apt install -y \
  python3-colcon-common-extensions \
  joystick jstest-gtk evtest \
  ros-${ROS_DISTRO}-twist-mux \
  ros-${ROS_DISTRO}-rosbridge-suite \
  ros-${ROS_DISTRO}-rqt \
  ros-${ROS_DISTRO}-rqt-image-view
```

### Schritt 3: Workspace kompilieren & sourcen

Now, build your ROS 2 workspace.

```bash
# Source your main ROS 2 installation
source /opt/ros/${ROS_DISTRO}/setup.bash

# Build the workspace
colcon build --symlink-install

# Source your local workspace overlay
source install/setup.bash
```

**Tip**: if this is your companion Computer you ran setup: Add `source ~/dev_ws_robot/install/setup.bash` to your `~/.bashrc` to source it automatically in new terminals.

## 🛠️ Build & Launch Commands

Common commands for everyday use.

### Simulation starten

```bash

ros2 topic list | zeigt alle topics
ros2 run joint_state_publisher_gui joint_state_publisher_gui
rviz2
rviz2 -d src/robot/config/view_robot.rviz
# Launch the full Gazebo simulation with the robot
ros2 launch robot launch_sim.launch.py

# Launch simulation in a specific world file
ros2 launch robot launch_sim.launch.py world:=src/robot/worlds/obstacles.world

# Launch only the Robot State Publisher and RViz (no Gazebo)
ros2 launch robot rsp.launch.py use_sim_time:=true
```

### Manuelle Steuerung

```bash
# Keyboard control (maps to /diff_cont/cmd_vel_unstamped)
ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r /cmd_vel:=/diff_cont/cmd_vel_unstamped

ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r /cmd_vel:=/mecanum_drive_controller/cmd_vel_unstamped
#Was ist anders? Wir leiten (-r) die Standardausgabe von /cmd_vel auf /mecanum_drive_controller/cmd_vel_unstamped um. Das ist der Name des Topics, auf dem dein Mecanum-Controller auf Befehle wartet.


# Joystick control (requires joy and teleop_twist_joy nodes)
# See config section for joystick setup
ros2 launch teleop_twist_joy teleop-launch.py
```

## 📋 ROS 2 Cheatsheet

A collection of useful commands for debugging and interaction.

### System & Topic Inspection

```bash
ros2 topic list                      # List all active topics
ros2 topic echo /diff_cont/odom      # Display messages from the odometry topic
ros2 param list                      # List all parameters of all nodes
ros2 run rqt_image_view rqt_image_view # Launch a GUI to view camera topics
```

### Controller Management (`ros2_control`)

```bash
# Check the status of controllers and interfaces
ros2 control list_hardware_interfaces
ros2 control list_controllers

# Spawn (activate) the controllers defined in your configuration
ros2 run controller_manager spawner diff_cont
ros2 run controller_manager spawner joint_broad
```

### Gazebo & Spawning

```bash
# Manually launch an empty Gazebo world
ros2 launch gazebo_ros gazebo.launch.py

# Manually spawn the robot model into a running Gazebo instance
ros2 run gazebo_ros spawn_entity.py -topic robot_description -entity robot
```

### WSL2 USB Controller Binding

To use physical hardware like a joystick connected via USB in WSL2, you must first bind it using PowerShell (as Administrator) in Windows.

```powershell
# Replace '1-1' with the correct BUSID of your USB device
usbipd bind --busid 1-1
```

### Zusammenfassung der ROS2 Humble & Gazebo Fehlersuche

Diese Tabelle fasst die häufigsten Probleme und deren Lösungen zusammen, die bei der Einrichtung einer `ros2_control`-basierten Simulation in Gazebo auftreten können.

| Schritt                       | Problembeschreibung                                                                                                                     | Zuständige Dateien                                                         | Befehle zur Diagnose                                                                                                      | Lösung                                                                                                                                                                                                                                                                                                                                                  |
| :---------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. Umgebung & Pakete**      | `Package 'gazebo_ros' not found` beim `ros2 launch`-Befehl.                                                                             | `Dockerfile`                                                               | `apt-cache policy ros-humble-gazebo-ros-pkgs` <br> `echo $AMENT_PREFIX_PATH`                                              | Die ROS2-Umgebung wurde nicht oder unvollständig geladen. **Lösung:** Fehlende Pakete im `Dockerfile` hinzufügen und das Image neu bauen. Vor jedem Start die ROS-Umgebung mit `source /opt/ros/humble/setup.bash` und den Workspace mit `source install/setup.bash` laden.                                                                             |
| **2. Gazebo Start**           | `Service /spawn_entity unavailable` <br> Der Roboter erscheint nicht in der leeren Gazebo-Welt.                                         | `launch/launch_sim.launch.py`                                              | `ros2 service list \| grep spawn_entity` <br> `ros2 node list`                                                            | Gazebo (`gzserver`) wurde ohne die notwendigen ROS-Plugins gestartet, die den Service zum Erstellen des Roboters bereitstellen. **Lösung:** `gzserver` im Launch-File explizit mit den Flags `-s libgazebo_ros_init.so` und `-s libgazebo_ros_factory.so` starten.                                                                                      |
| **3. Controller-Konflikt**    | `gzserver` oder `gzclient` stürzen ab (z.B. `exit code 255`). <br> Controller-Fehler wie `STRICT switch failures`.                      | `launch/launch_sim.launch.py` <br> `launch/launch_sim.launch.old.py`       | `ros2 control list_controllers` <br> Launch-Logs auf doppelte Spawner-Nodes prüfen.                                       | Die `ros2_control`-Controller wurden von zwei Quellen gestartet: einmal automatisch durch das `gazebo_ros2_control`-Plugin und zusätzlich durch externe `spawner`-Nodes im alten Launch-File. **Lösung:** Alle externen `spawner`-Nodes aus dem Launch-File entfernen.                                                                                  |
| **4. RViz-Visualisierung**    | In RViz erscheinen `No transform from [wheel] to [chassis]`-Fehler. Das Robotermodell ist unvollständig.                                | `config/view_robot.rviz`                                                   | `ros2 topic hz /joint_states` <br> `ros2 topic echo /tf --once`                                                           | Der `joint_state_broadcaster` (der die Gelenk-Daten liefert) war nicht aktiv. Dadurch fehlten die `/joint_states`-Nachrichten, die der `robot_state_publisher` zur Berechnung der Transformationen (TF) benötigt. **Lösung:** Den `joint_state_broadcaster` explizit im Launch-File starten.                                                            |
| **5. Controller-Startfehler** | Die Controller (`mecanum_drive_controller`, `joint_state_broadcaster`) starten nicht, obwohl sie im Log als "geladen" angezeigt werden. | `config/my_controllers_mecanum.yaml` <br> `description/ros2_control.xacro` | `ros2 control list_controllers` (zeigt leere Liste) <br> Launch-Logs auf Fehlermeldungen des `controller_manager` prüfen. | Die Parameter in der `.yaml`-Datei entsprachen nicht exakt den Namen, die die spezifische Version des `mecanum_drive_controller` erwartet (z.B. `kinematics.wheels_radius`). **Lösung:** Die `my_controllers_mecanum.yaml` an die exakte Struktur und Parameternamen aus der Fehlermeldung bzw. der Controller-Dokumentation anpassen.                  |
| **6. Keine Roboterbewegung**  | Der Roboter reagiert nicht auf Steuerbefehle, obwohl die Simulation fehlerfrei läuft und die Controller aktiv sind.                     | `config/my_controllers_mecanum.yaml` <br> (Befehl im Terminal)             | `ros2 topic echo <topic_name>` <br> `rqt_graph`                                                                           | Der Steuerungs-Node (z.B. `teleop_twist_keyboard`) und der `mecanum_drive_controller` kommunizierten auf unterschiedlichen Topics. **Lösung:** Das richtige Kommando-Topic des Controllers (`/mecanum_drive_controller/reference_unstamped`) herausfinden und den Steuerungs-Node mit einem Remapping darauf umleiten (`--ros-args -r /cmd_vel:=/...`). |

# Finaler ROS2 Humble & Gazebo Troubleshooting Guide

Diese Anleitung fasst den gesamten Debugging-Prozess zusammen, um eine `ros2_control`-basierte Simulation mit einem Mecanum-Roboter in Gazebo zum Laufen zu bringen.

| Schritt                         | Problembeschreibung                                                                                                                  | Zuständige Dateien                                                       | Befehle zur Diagnose & Fehleranalyse                                                                                                                                                                                                                                                                                                                                                                                                                                        | Lösung                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| :------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Umgebung & Pakete**        | Der `ros2 launch`-Befehl schlägt mit `Package 'gazebo_ros' not found` fehl. Die ROS2-Umgebung ist unvollständig.                     | `Dockerfile`                                                             | 1. **Paket-Installation prüfen:**<br>`apt-cache policy ros-humble-gazebo-ros-pkgs`<br>*(Zeigt an, ob das Paket überhaupt im System bekannt ist.)*<br>2. **Umgebungsvariablen prüfen:**<br>`echo $AMENT_PREFIX_PATH`<br>*(Muss den Pfad zu `/opt/ros/humble/...` enthalten.)*<br>3. **ROS2-Installation sourcen:** Sicherstellen, dass `source /opt/ros/humble/setup.bash` ausgeführt wurde.                                                                                 | Die notwendigen ROS2-Pakete für die Simulation waren nicht im Docker-Image installiert. **Lösung:** Alle Abhängigkeiten (wie `ros-humble-gazebo-ros-pkgs`, `ros-humble-ros2-control` etc.) explizit im `Dockerfile` hinzufügen und das Image neu bauen.                                                                                                                                                                                                                                 |
| **2. Gazebo & Roboter-Spawn**   | Gazebo startet mit einer leeren Welt, aber der Roboter erscheint nicht. Der Spawner-Node meldet `Service /spawn_entity unavailable`. | `launch/launch_sim.launch.py`                                            | 1. **Service-Verfügbarkeit prüfen:**<br>`ros2 service list \| grep spawn_entity`<br>*(Wenn der Service fehlt, wurden die Gazebo-Plugins nicht geladen.)*<br>2. **Laufende Knoten prüfen:**<br>`ros2 node list`<br>*(Sicherstellen, dass `/gazebo` läuft.)*<br>3. **Spawner-Logs analysieren:** Die Fehlermeldung `Was Gazebo started with GazeboRosFactory?` ist der direkte Hinweis.                                                                                       | `gzserver` (der Gazebo-Server) wurde ohne die entscheidenden ROS2-Plugins gestartet. **Lösung:** Gazebo im Launch-File nicht über `IncludeLaunchDescription` starten, sondern als `ExecuteProcess` mit expliziten Flags, um die ROS-Plugins zu laden: `cmd=['gzserver', ..., '-s', 'libgazebo_ros_init.so', '-s', 'libgazebo_ros_factory.so', ...]`                                                                                                                                     |
| **3. Controller-Start & URDF**  | RViz zeigt `No transform from [wheel] to [chassis]`-Fehler. Das Robotermodell ist unvollständig ("zerfallen").                       | `config/my_controllers_mecanum.yaml`<br>`description/ros2_control.xacro` | 1. **Controller-Status prüfen:**<br>`ros2 control list_controllers`<br>*(Die Ausgabe ist leer oder zeigt die Controller als `inactive`.)*<br>2. **Gelenk-Daten prüfen:**<br>`ros2 topic hz /joint_states`<br>*(Zeigt `WARNING: topic ... does not appear to be published yet`.)*<br>3. **Controller Manager Logs prüfen:** Die `gzserver`-Ausgabe auf Fehlermeldungen wie `Could not initialize controller` oder `Parameter ... cannot be empty` prüfen.                    | Die `ros2_control`-Controller (`joint_state_broadcaster`, `mecanum_drive_controller`) wurden nicht korrekt geladen, weil die Parameter in der `.yaml`-Datei nicht exakt mit den Erwartungen der Controller-Version übereinstimmten. **Lösung:** Die `my_controllers_mecanum.yaml` an die exakte Struktur und die Parameternamen aus der Fehlermeldung anpassen. Die `ros2_control.xacro` muss auf diese eine korrekte Datei verweisen.                                                  |
| **4. Odometrie-Visualisierung** | Nach dem Wechsel des "Fixed Frame" in RViz auf `odom` erscheinen Fehler wie `Frame [odom] does not exist`.                           | `launch/launch_sim.launch.py`<br>`launch/tf_odometry_relay.py`           | 1. **TF-Daten prüfen:**<br>`ros2 topic echo /tf --once`<br>*(Die Transformation von `odom` nach `base_link` fehlt in der Ausgabe.)*<br>2. **Private TF-Daten des Controllers prüfen:**<br>`ros2 topic hz /mecanum_drive_controller/tf_odometry`<br>*(Hier werden die Daten veröffentlicht.)*<br>3. **Laufende Knoten prüfen:**<br>`ros2 node list`<br>*(Prüfen, ob der `tf_odometry_relay`-Knoten läuft.)*                                                                  | Der `mecanum_drive_controller` veröffentlicht die Odometrie-Transformation nicht auf dem globalen `/tf`-Topic, sondern privat. **Lösung:** Einen Relay-Knoten (`tf_odometry_relay.py`) im Launch-File starten, der die Nachrichten von `/mecanum_drive_controller/tf_odometry` abonniert und auf `/tf` weiterleitet.                                                                                                                                                                    |
| **5. Roboterbewegung**          | Die Simulation läuft komplett fehlerfrei, aber der Roboter reagiert nicht auf Steuerbefehle.                                         | (Terminal-Befehl)<br>`todo.md`                                           | 1. **Verbindung visualisieren:**<br>`rqt_graph`<br>*(Zeigt, dass der Steuerungs-Node (z.B. `teleop_twist_keyboard`) keine Verbindung zum `mecanum_drive_controller` hat.)*<br>2. **Nachrichten auf dem Ziel-Topic prüfen:**<br>`ros2 topic echo <topic_name>`<br>*(Zeigt an, ob überhaupt Nachrichten ankommen.)*<br>3. **Manuell einen Befehl senden:**<br>`ros2 topic pub --once <topic_name> ...`<br>*(Um zu testen, ob der Controller überhaupt auf Befehle reagiert.)* | Der Steuerungs-Node und der `mecanum_drive_controller` kommunizierten auf unterschiedlichen Topics. Der Controller erwartete Befehle auf `/mecanum_drive_controller/reference_unstamped`, nicht auf dem Standard-Topic `/cmd_vel`. **Lösung:** Den Steuerungs-Node mit einem Remapping-Argument starten, um die Ausgabe auf das richtige Topic umzuleiten: `ros2 run teleop_twist_keyboard teleop_twist_keyboard --ros-args -r /cmd_vel:=/mecanum_drive_controller/reference_unstamped` |


# ROS2 Humble & Gazebo: Troubleshooting-Guide

Diese Tabelle fasst die häufigsten Probleme und deren Lösungen zusammen, die bei der Einrichtung einer `ros2_control`-basierten Simulation in Gazebo auftreten können, basierend auf unserer Fehlersuche.

| Schritt                           | Problembeschreibung                                                                                                                                           | Zuständige Dateien                                                     | Befehle zur Diagnose                                                                                                                                                                                                                                                                                                           | Lösung                                                                                                                                                                                                                                                                                                                                                                                                        |
| :-------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. Umgebung & Pakete**          | `Package not found`-Fehler beim `ros2 launch` (z.B. für `gazebo_ros`, `teleop_twist_keyboard`).                                                               | `Dockerfile`, `.bashrc`                                                | **1.1** Paketinstallation prüfen: `apt-cache policy ros-humble-<paket-name>` <br> **1.2** ROS2-Umgebung prüfen: `echo $AMENT_PREFIX_PATH` (muss `/opt/ros/humble` enthalten) <br> **1.3** Workspace-Overlay prüfen: `echo $AMENT_PREFIX_PATH` (muss auch den Pfad zum `install`-Verzeichnis deines Workspaces enthalten)       | Die ROS2-Umgebung wurde nicht oder unvollständig geladen, oder ein benötigtes Paket wurde im Docker-Image nicht installiert. <br> **Lösung:** Fehlende Pakete im `Dockerfile` hinzufügen und das Image neu bauen. Vor jeder Aktion sicherstellen, dass die ROS-Umgebung (`source /opt/ros/humble/setup.bash`) und der Workspace (`source install/setup.bash`) geladen sind.                                   |
| **2. Build-System**               | `libexec directory ... does not exist`-Fehler beim Starten eines Python-Skripts als `Node`.                                                                   | `CMakeLists.txt`, `launch/*.launch.py`                                 | **2.1** Installations-Verzeichnis prüfen: `ls -R install/robot` (suchen nach `lib/robot`)                                                                                                                                                                                                                                      | Ein Python-Skript wurde im Launch-File als `Node` deklariert, aber in der `CMakeLists.txt` nicht als ausführbares Programm installiert. <br> **Lösung:** Das Skript im Launch-File als `ExecuteProcess` mit `cmd=['python3', 'pfad/zum/skript.py']` starten. Dies umgeht die Notwendigkeit, die `CMakeLists.txt` zu ändern.                                                                                   |
| **3. Gazebo & Roboter-Spawn**     | `Service /spawn_entity unavailable`. <br> Gazebo startet, aber der Roboter erscheint nicht.                                                                   | `launch/launch_sim.launch.py`                                          | **3.1** Aktive Services auflisten: `ros2 service list` (prüfen, ob `/spawn_entity` vorhanden ist) <br> **3.2** ROS-Knoten in Gazebo prüfen: `ros2 node list` (prüfen, ob `gzserver` läuft)                                                                                                                                     | Der Gazebo-Server (`gzserver`) wurde ohne die notwendigen ROS-Plugins gestartet, die den Service zum Erstellen des Roboters bereitstellen. <br> **Lösung:** `gzserver` im Launch-File explizit mit den Flags `-s libgazebo_ros_init.so` und `-s libgazebo_ros_factory.so` starten.                                                                                                                            |
| **4. Controller-Initialisierung** | Controller-Fehler in den Logs, z.B. `Parameter ... cannot be empty` oder `kinematics.wheels_radius must be > 0`. Der `spawner`-Node stirbt mit `exit code 1`. | `config/my_controllers_mecanum.yaml`, `description/ros2_control.xacro` | **4.1** Controller-Status prüfen: `ros2 control list_controllers` <br> **4.2** Detaillierte `gzserver`-Logs analysieren (mit `--verbose` gestartet), um die genaue Fehlermeldung des `controller_manager` zu finden.                                                                                                           | Die Parameter in der `.yaml`-Datei entsprachen nicht exakt den Namen oder der Struktur, die die spezifische Version des `mecanum_drive_controller` erwartet. <br> **Lösung:** Die `my_controllers_mecanum.yaml` exakt an die Struktur und Parameternamen aus der Fehlermeldung anpassen und sicherstellen, dass die `ros2_control.xacro` auf diese korrekte Datei verweist.                                   |
| **5. TF & RViz-Visualisierung**   | In RViz erscheinen `No transform`-Fehler (z.B. von `base_link` zu `odom`). Das Robotermodell ist unvollständig oder "explodiert".                             | `launch/launch_sim.launch.py`, `*.rviz`                                | **5.1** Überprüfen, ob Odometrie-TF veröffentlicht wird: `ros2 topic echo /tf --once` (suchen nach `odom` -> `base_link`) <br> **5.2** `joint_states` prüfen: `ros2 topic hz /joint_states` (muss eine Frequenz haben) <br> **5.3** RViz-Zeitquelle prüfen: In RViz unter `Global Options` muss `Use Sim Time` aktiviert sein. | **Problem A:** Der `joint_state_broadcaster` war nicht aktiv. **Problem B:** Der `mecanum_drive_controller` veröffentlicht die `odom`-TF auf einem privaten Topic. <br> **Lösung:** Controller explizit mit `spawner`-Nodes im Launch-File starten und einen `tf_odometry_relay`-Knoten hinzufügen, der die private TF auf das globale `/tf`-Topic weiterleitet.                                              |
| **6. Keine Roboterbewegung**      | Simulation läuft fehlerfrei, Controller sind aktiv, aber der Roboter reagiert nicht auf Steuerbefehle.                                                        | (Befehl im Terminal)                                                   | **6.1** Topic-Verbindungen visualisieren: `rqt_graph` <br> **6.2** Manuell einen Befehl publizieren: `ros2 topic pub --once <topic_name> geometry_msgs/msg/Twist "{...}"` <br> **6.3** Eingehende Nachrichten prüfen: `ros2 topic echo <topic_name>`                                                                           | Der Steuerungs-Node (z.B. `teleop_twist_keyboard`) und der `mecanum_drive_controller` kommunizierten auf unterschiedlichen Topics. <br> **Lösung:** Das korrekte Kommando-Topic des Controllers (`/mecanum_drive_controller/reference_unstamped`) herausfinden (z.B. durch Ausprobieren oder Doku) und den Steuerungs-Node mit einem Remapping darauf umleiten (`--ros-args -r /cmd_vel:=<korrektes_topic>`). |
